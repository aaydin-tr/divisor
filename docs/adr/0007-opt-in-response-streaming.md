# Response streaming is opt-in, decided per response, and every wait on a streaming Backend stays bounded

With `server.streaming: true` (default **false**), divisor forwards a Backend response as a **Streamed response** (CONTEXT.md) when its `Content-Type` media type is `text/event-stream` (parameters ignored) or it declares no `Content-Length`. The rule is applied to each response, from the Backend's headers. Every other response — a declared length that is not an event stream, and HEAD/204/304, which carry no body — is read whole and takes the buffered path unchanged, `OnResponse` body rewrites included. Both stacks stream: fasthttp forwards the body chunked and flushes after every read (an event stream that declared a length too, since a fixed-length write is not flushed per read); the net/http adapter flushes the headers at once and every write after them. This supersedes review L8's "unsupported in 1.0" and amends ADR 0003 twice.

**Timeout model** (amends ADR 0003's Consequences). `proxy_timeout` bounds a Streamed response until the Backend's status and headers arrive; expiry is the same 504. From then on `server.stream_idle_timeout` (default 5m) bounds each wait for more body bytes from the Backend and each write of them to the client, so a client that stays connected but stops reading is reaped too; both are re-armed on every read, and expiry ends the stream. As with `proxy_timeout`, `0` means the default and there is no unlimited setting, so no wait on either side of a stream is unbounded; a stream that keeps flowing has no total lifetime bound.

**Cancellation** (amends ADR 0003's L6 note). A client that disconnects mid-stream aborts its Backend stream at once on both stacks, and the Backend connection is closed instead of pooled. On fasthttp a goroutine reads the client connection while the stream runs (an HTTP/1.1 client sends nothing while its response arrives, so the read returns only when the client leaves); on net/http the end of `r.Context()` does it. Buffered requests keep the L6 position — no cancellation, bounded by `proxy_timeout` — and so does a would-be stream until its headers arrive, since `fasthttp.HostClient` has no cancellation hook.

**Middleware.** `OnRequest` is unchanged. `OnResponse` runs once a Streamed response's status and headers arrive, before its first body byte is forwarded: `ctx.Response` holds them with an empty body, status and header changes are forwarded, a body it sets is dropped, `ErrShortCircuit` replaces the stream with the response it wrote (the Backend stream is closed), and any other error is the usual 500. No Middleware ever sees a Streamed response's body.

**Selection.** A stream feeds the response-time score its time to headers, not its duration, and counts as a Pending request until it ends, which is what least-connection should see.

## Considered Options

- **Streaming on by default** — rejected for 1.0: upgrading must not change the traffic of anyone who did not opt in. A 1.1 candidate; the knob goes away then.
- **Stream only `text/event-stream`** — rejected: a chunked download would still be held whole in memory.
- **Stream every response** — rejected: `OnResponse` would lose body rewrites on all traffic, so turning the knob on would not be safe for mixed traffic.
- **`proxy_timeout` over the whole stream** — rejected: it ends every SSE stream at `proxy_timeout`. **An unlimited idle timeout** — rejected for ADR 0003's reason: a silent Backend would hold a connection forever.
- **Bound only the reads from the Backend** — rejected: with `write_timeout` at its default 0, a client that stays connected but stops reading would hold its stream, and the stream's Backend connection, forever.
- **Score a stream by its duration** — rejected: a one-hour stream would make its Backend look pathologically slow to least-response-time.
- **Cancel buffered requests too** — not taken: fasthttp's client cannot cancel an attempt, and `proxy_timeout` already bounds one. A stream is the case where a gone client otherwise costs a Backend connection for as long as the Backend keeps sending.
- **On fasthttp, notice a gone client only when a write fails** — rejected: a silent stream would hold its Backend connection until `stream_idle_timeout`. The alternatives to the read watch were worse: `Connection: close` on every stream loses keep-alive after it, `MSG_PEEK` is unreachable through fasthttp's per-IP and TLS connection wrappers, and hijacking ends keep-alive too.
- **A buffer-and-inspect API giving Middleware a stream's body** — rejected for 1.0.
- **Request streaming** — deferred past 1.0: uploads stay buffered so `max_request_body_size` can answer 413 before a Backend sees the body.

## Consequences

- A non-zero `server.write_timeout` caps a stream's whole lifetime on both stacks: the per-write client deadline divisor arms (fasthttp `RequestCtx.SetWriteDeadline`, net/http `ResponseController.SetWriteDeadline`) replaces the server's own but never reaches past its expiry; the cut is logged as `write timeout`. Its default, 0, leaves streams alone. `server.read_timeout` does not affect a stream on either stack.
- A stream that ends any way but the Backend finishing it never looks complete to the client: HTTP/2 resets the stream (`RST_STREAM INTERNAL_ERROR`), HTTP/1.1 closes the connection without the terminating chunk.
- Backend trailers on a Streamed response are dropped.
- An open stream holds one Backend connection until it ends, so `backends[].max_conn` caps concurrent streams per Backend. A request past the cap waits for a free connection for `max_conn_timeout` or `proxy_timeout`, whichever is shorter, then fails: 502, or 504 when `proxy_timeout` was the shorter.
- With streaming on, a buffered response whose body breaks mid-read is a 502 (504 on a deadline) without the idempotent-request retry fasthttp performs with streaming off.
- A client half-close (shutting down its write side) counts as a disconnect on both stacks, as it does for net/http's own background read.
- On fasthttp, a request pipelined behind an open stream is never forwarded: the watch consumed its first byte, so the connection closes after the stream, without the terminating chunk, and the client must resend.
- Every stream end logs one debug line, `Streamed response ended`, with `cause` (`backend closed`, `backend failed`, `idle timeout`, `client disconnected`, `write timeout`, `replaced by middleware`) and `forwarded_bytes`; the first cause wins. `idle timeout` names a silent Backend and a client write blocked for `stream_idle_timeout` alike. net/http ends `r.Context()` for a gone client and at `write_timeout` alike, so the adapter names `write timeout` when the request has run for at least `write_timeout` minus 100ms.
- **Access log**: a Streamed request's line is written when the stream ends, whatever the cause. `duration_ms` runs from request start to stream end; `bytes_out` counts body bytes written to the client connection (a chunk whose write failed or timed out is not counted); `status` is the one sent at stream start even if the stream was cut later; `time` is when the line was written, so lines are not in request-start order. Why a stream ended is only in the debug line. A Short-circuit that replaced a stream logs one line, for its own response.
- **Graceful shutdown**: an open stream is a Pending request and nothing ends it on shutdown. Streams that end during the drain let it complete; one still open at `server.graceful_shutdown_timeout` makes the drain time out — fasthttp's `ShutdownWithContext` and net/http's `Shutdown` both wait for it and return `context.DeadlineExceeded` (verified 2026-10-29) — and divisor exits 1, cutting the stream without an Access log line.
- A Reload that removes a Backend leaves its open streams running until they end (ADR 0006: requests already on a removed Backend finish).
- The idle deadline needs the Backend connection, which fasthttp does not expose on a client response; divisor wraps the dialer so the response's `LocalAddr()` carries it. If a fasthttp bump breaks that, streams end at `proxy_timeout` again; `TestStreamOutlivesProxyTimeoutWhileDataFlows` fails first.
