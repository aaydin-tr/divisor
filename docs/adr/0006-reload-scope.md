# A Reload changes only the Backend set and Probe settings, and is all-or-nothing

A **Reload** (CONTEXT.md) re-reads the config file into the running process. It may change only `backends` (every entry key, so the per-Backend Probe settings `health_check_path` / `health_check_status` included), `health_checker_time` and `health_checker_timeout`. `config.PlanReload` compares the running and the new config — both prepared, so writing out a default is no change — key by key over their YAML tags; any other key that differs rejects the **whole** Reload, and the log names every such key (`server.proxy_timeout`, not `server`). A new config that does not parse or validate is rejected the same way. A rejected Reload changes nothing: divisor keeps serving the running config, and the next Reload is compared against that config, not against the rejected file. A key added to `Config` later is restart-only unless it is added to the reloadable set on purpose.

The Backend set is diffed by entry, not by position. A new entry equal to a running one (after URL normalization and defaults) keeps that Backend — its Index, liveness, stats and connections — wherever it moved in the list; any changed key makes it a different Backend, so a changed entry is a removal plus an addition. Equal duplicates pair up in list order. Added Backends get an Index the process never used before (the boot-time ones are the config positions 0..n-1), are Probed once during the Reload and Join if Alive; only then do removed Backends Leave and close their idle connections, so replacing every Backend never empties the rotation in between. Requests already on a removed Backend finish. `/stats` lists the new config order with each Backend's Index as `backend_hash`; `/metrics` drops the series of an address no Backend has any more.

Two triggers call the one entry point, `reload.Reloader.Reload`, which serializes Reloads and is closed as graceful shutdown starts, right after `/ready` turns 503 (it waits for a Reload in flight, inside `graceful_shutdown_timeout`): SIGHUP, and a change to the config file. The file watch (`reload.ConfigFileWatch`, fsnotify) watches the config file's directory, because kubelet updates a ConfigMap volume without ever writing `config.yaml`: it writes a new timestamped data directory and renames a `..data_tmp` symlink over `..data`, through which `config.yaml` resolves. An event counts as a change when it names the config path (a write, an editor's atomic save, a removal; attribute-only changes do not count) or when the config path now resolves to a different file. Changes Reload once the config file has been left alone for one second (`reload.ConfigFileQuietPeriod`), so a burst — a ConfigMap swap, an editor's rename dance, a non-atomic multi-write save — is one Reload, read after the writing stopped. The watch starts before divisor reads its config at boot and queues changes until the Reloader exists, so an edit landing during startup (the first Probe round can take seconds) is applied, not lost. If the watch cannot start, divisor logs why and serves on; SIGHUP still Reloads.

## Considered Options

- **Apply the reloadable part, ignore the rest** — rejected: the file would say one thing and the process do another until some later restart picked up the ignored keys, possibly long after the edit. Rejecting loudly keeps "the file is what runs" true except for the one logged moment it is not.
- **Rebuild the Pool and Balancer from scratch on every Reload** — rejected: every Backend would lose its stats, its response-time score and its liveness (a Down Backend would briefly look Alive or vice versa), and ip-hash would rehash every client instead of only those the added or removed Backends move.
- **Renumber Indexes to the new config positions** — rejected: `backend_hash` would point at a different Backend after a Reload (the monitoring page keys its charts by it), and ip-hash derives ring positions from the Index, so a survivor that moved would move its clients too.
- **Treat an entry whose only change is its position as changed** — rejected: reordering the list is not a change to any Backend.
- **Watch the config file itself** — rejected: the watch follows the file's inode, which an atomic save or a ConfigMap update replaces, so the first such edit would be the last one seen.
- **Reload on every event in the config file's directory** — rejected: a debounce restarted by every unrelated write in a busy directory could postpone a Reload indefinitely, and each burst would log a no-op Reload.
- **Skip a file-change Reload whose bytes equal the last read** — not done: once events are filtered to the config file, same-content changes are rare, and an unchanged file is already a valid Reload that changes nothing.

## Consequences

- `backend_hash` equals the config index only until the first Reload that adds a Backend.
- `w-round-robin` with a single Backend runs as `round-robin` (`PrepareConfig`); a Reload that crosses one Backend in either direction would change the running Balancer, so it is rejected naming `type`.
- An added Backend's first Probe runs inside the Reload, so a Reload adding unreachable Backends takes up to `health_checker_timeout` per such Backend, during which Probe rounds wait.
- The ip-hash Balancer keeps a reference to every Backend it ever Joined (a `Pick` may resolve a ring snapshot from before a `Leave`); a removed Backend costs one small struct for the life of the process.
- A config file edit takes effect about a second after the last write, and a continuous stream of writes to the config file postpones its Reload until the stream stops.
- Some edits raise no event in the watched directory and need SIGHUP: writing through a symlink into another directory (e.g. into `..data/config.yaml` in place), and a host-side edit of a single file bind-mounted into a container. A ConfigMap mounted with `subPath` is never updated by kubelet at all; mount the volume as a directory.
- An edit that leaves the file's content as it was (an editor saving without changes) logs a Reload that changes nothing.
